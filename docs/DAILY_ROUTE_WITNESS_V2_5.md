# 每日维护路线 witness：v2.5

日期：2026-09-19。此实验只检查已经存在的 FEED / HARVEST / 临近成熟 WATER 是否能在一天余下时间里走完；不新增作物/动物，不改 V45，不发 Kaggle 提交。

## 先纠正观测时机

初版 v2.3 在每天 hour 0 看工人。那时前一天的雇工已消失，而当天的 V45 会在该回合市场订单中 `HIRE`；于是它常常只看到一个农夫，把全部维护工作错误压给一人。其“1,624 天排不下”没有解释价值。

v2.4/v2.5 改在 hour 1 记录：第一个回合的 HIRE 已被官方引擎处理，观察中是实际成功雇到的雇工、实际出生位置和农夫完成首个动作后的农场。当天还剩 23 回合。这比预先猜 HIRE 是否买得起、雇工出生在哪更可靠。

## v2.5 排程方式

同一格的任务会合并，让一位工人走到一次后连续做完。每一步先只考虑当前最高优先级的未完成任务，再在所有“工人—任务”搭配中选择完成时间最早的一对；走路使用游戏中精确的曼哈顿最短距离（锁地可以穿过），每个田间操作计 1 回合。

成功表示：存在这条具体的贪心路线。失败表示：这个贪心路线没找到，不是数学上证明没有任何路线。它没有安排市场操作、未来 HIRE、携带/送货、未来发生的任务或新增投资。

## 验证和结果

- 3 个回归测试通过；
- 固定 56 局开发条件全部 `DONE/DONE`，56/56 终局现金严格复现冻结 V45；
- 记录 1,680 份 hour-1 日计划；
- v2.4 的旧固定坐标顺序能证明 724 天；v2.5 的动态同优先级选择能证明 924 天，新增 200 天，零回退；
- 756 天仍未获得贪心路线；集中在第 15–28 天；
- 每一份未获得路线的计划，其任务操作数都小于“实际雇工数 × 23 回合”。故目前不能说是纯动作数量不够，只能说移动路径/任务分配需要更好求解；
- 在 868 个“有维护任务且已给出具体路线”的日子里，完成维护后仍余下行动格的中位数为 66。这个数字**不能**直接用于投资，因为还没预留携带、送货、市场和新增任务。

## 结论

现在已经可以严肃地说：V45 中后期有很多维护任务，走路是必须纳入的限制；也可以说固定坐标顺序会错误制造“排不下”。但还不能从 924/1,680 推出 V45 只有约一半天能维护，也不能从 66 推出可再养多少动物。

下一步如继续，需审核一个“多种确定性排程 witness”的对照：在相同任务和雇工下运行动态最早完成、按空间分区、按最近邻等多个固定构造；任一成功都提供可行路线，全部失败仍只称为“这些构造均未找到”。这样先区分剩余 756 天主要是贪心缺陷还是地图/任务密度问题，仍不发动作。
